# 03. Аудит надёжности (главный приоритет)

> Фокус: устойчивость приложения «в бою» — краши, сеть, фоновые сервисы, локация,
> жизненный цикл, восстановление после сбоев. Игра ещё предстоит и может повторяться,
> поэтому приоритет — чтобы у игрока на телефоне ничего не падало и не «отваливалось».
>
> Метод: статический разбор «хребта» приложения (Application, сервисы, MainActivity,
> Auth, сеть) + прицельный grep по системным паттернам. Динамическая проверка — в
> [07-dynamic-testing.md](07-dynamic-testing.md).

## Резюме

Приложение в целом «работает», и видно, что над стабильностью думали: везде try/catch,
логирование, foreground-сервис с уведомлением, дефолты при ошибках сети (пустые списки,
показ контента даже при HTTP-ошибке). Это хорошо и для игрового клиента разумно.

Но надёжность держится на «обмазывании try/catch», а не на архитектуре. Есть несколько
конкретных проблем, которые в полевых условиях (слабая сеть, старый телефон, долгая
сессия, повороты экрана, уход в фон на часы) приведут к тому, что:

- на части телефонов (**Android 12 и ниже**) кнопка карты может вообще не включаться;
- фоновый сбор точек/сообщений — это поллинг каждые 30–60 с, устойчивый к сети, но
  прожорливый и с риском не пережить Doze/убийство процесса на «китайских» прошивках;
- самообновление скачивает и ставит APK **без проверки целостности** (риск и надёжности,
  и безопасности);
- утечки/«висячие» корутины через `GlobalScope`, гонки в апдейтере.

Ни одна из проблем не является «приложение падает при старте», но каждая — это «в
определённый момент игры у конкретного игрока что-то тихо перестало работать», а для
игры на выезде это дороже, чем красивый краш.

## Детальные находки

### R1 (High). `POST_NOTIFICATIONS` без проверки версии ОС — карта недоступна на Android ≤ 12

`hasNotificationPermission()` безусловно вызывает
`checkSelfPermission(POST_NOTIFICATIONS)` без ветки по `Build.VERSION.SDK_INT`:

```kotlin
// MainActivity.kt:607
private fun hasNotificationPermission(): Boolean =
    ContextCompat.checkSelfPermission(this, Manifest.permission.POST_NOTIFICATIONS) == PERMISSION_GRANTED
```

`POST_NOTIFICATIONS` появился только в API 33 (Android 13). На API 26–32 (а `minSdk = 26`)
эта проверка вернёт `DENIED`, а запрос разрешения будет проигнорирован системой. При этом
доступ к карте жёстко завязан на это разрешение:

```kotlin
// MainActivity.kt:190
if (ShiftApplication.instance.isInGame() && hasNotificationPermission()) { startActivity(... EkatMaps ...) }
// MainActivity.kt:303
binding.btnOpenMap.isEnabled = ShiftApplication.instance.isInGame() && hasNotificationPermission()
```

**Итог:** на телефонах с Android 12 и ниже кнопка «Карта» останется выключенной навсегда,
а часть логики разрешений зациклится на запросе несуществующего разрешения.
Контраст: `MessagesChatActivity.kt:512` тот же случай обрабатывает правильно, через
`if (SDK_INT >= TIRAMISU)`. То есть паттерн в проекте известен — просто не применён в
главном экране.

**Починка:** обернуть проверку/запрос `POST_NOTIFICATIONS` в `if (SDK_INT >= 33)`, а на
старых версиях считать разрешение выданным (или, лучше, вообще не завязывать доступность
карты на разрешение уведомлений — это разные вещи).

**Проверка:** нужен прогон на эмуляторе/устройстве с API ≤ 32 (текущий эмулятор — API 35,
на нём не воспроизводится). Логика однозначна, риск высокий.

### R2 (High). Самообновление ставит APK без проверки целостности + гонка двойной установки

`UpdateService` читает из `update.json` поле `sha256`:

```kotlin
// UpdateService.kt:123
sha256 = json.optString("sha256").takeIf { it != "PUT_YOUR_APK_SHA256" }
```

…но **нигде дальше `sha256` не используется**. `downloadAndInstallUpdate()` просто качает
файл `DownloadManager`-ом и запускает установщик. Нет ни проверки хеша, ни проверки подписи.

Последствия для надёжности: если загрузка побилась (обрыв сети, неполный файл, кэш прокси),
пользователю всё равно откроется установщик битого APK — установка упадёт с непонятной
ошибкой в разгар игры. Проверка `sha256` (которая уже задумана!) отсекала бы это.
Плюс security-аспект: `url` берётся из JSON и может оказаться `http://…` → MITM-подмена APK
(подробно — в [05-security.md](05-security.md)).

Дополнительно — **гонка двойной установки**. Завершение отслеживается сразу двумя путями:
1. `BroadcastReceiver` на `ACTION_DOWNLOAD_COMPLETE` (`UpdateService.kt:208`);
2. корутина-таймер `delay(5000)` (`UpdateService.kt:284`).

Если загрузка укладывается в 5 секунд, оба пути видят `STATUS_SUCCESSFUL` и оба вызывают
`installApk()` → два интента установщика. `unregisterReceiver` вызывается в обоих, второй —
кинет `IllegalArgumentException` (обёрнут в try/catch, но это симптом гонки).

**Починка:** проверять `sha256` скачанного файла перед установкой (SHA-256 файла ==
ожидаемому); один источник события завершения (receiver **или** периодический опрос, не оба);
требовать HTTPS для `url`.

### R3 (High). `GlobalScope.launch` для сетевых операций UI → утечки и обращение к мёртвому UI

В `MainActivity` шесть использований `GlobalScope` (grep подтвердил — все в этом файле):

```kotlin
// MainActivity.kt:405 loadUserAura
GlobalScope.launch(Dispatchers.Main) { val r = RetrofitClient.auraApi.getAura(userId); ... updateAuraButton() }
// MainActivity.kt:442 toggleAuraHidden — Toast(this@MainActivity) после ответа
// MainActivity.kt:799 performRitual — createPoint + runOnUiThread { Toast, binding.* }
```

`GlobalScope` не привязан к жизненному циклу Activity. Проблемы:
- корутина удерживает ссылку на `MainActivity`/`binding` до завершения сетевого вызова —
  при закрытии экрана Activity не собирается GC → утечка (на слабой сети — секунды–десятки секунд);
- по возвращении из сети код трогает `binding` и показывает `Toast(this@MainActivity)`.
  На уже уничтоженной Activity показ Toast/диалога может кинуть
  `BadTokenException`/`WindowManager` ошибку;
- при повороте экрана «в полёте» результат применится к старому, уже невалидному экрану.

Это системный паттерн (весь async в MainActivity так написан), поэтому severity High несмотря
на то, что «обычно проносит».

**Починка:** заменить `GlobalScope` на `lifecycleScope` (Activity его уже поддерживает —
используется в `EffectEditorActivity`/`EkatMaps`), тогда корутины сами отменятся в `onDestroy`.
Перед обращением к UI из колбэков Retrofit — проверять `isFinishing/isDestroyed` (частично уже есть).

### R4 (Medium). Фоновая механика = ручной поллинг; уязвим к Doze и убийству процесса

`LocationService` держит `isActive` и три `Handler.postDelayed`-цикла + колбэк локации:

- точки в радиусе — каждые 30 с (`pointsCheckRunnable`, `LocationService.kt:60`);
- профиль — каждые 60 с (`profileUpdateRunnable`, `:71`);
- сообщения — каждые 60 с (`messagesCheckRunnable`, `:82`);
- отправка локации — из колбэка каждые 30 с (`:99`).

Плюсы: как foreground-сервис с типом `location` он живёт в фоне, и это правильный выбор для
геймплея «вошёл в зону → уведомление». Логика входа/выхода из точек (`checkPointsInRange`,
`onEnterPoint/onExitPoint`) аккуратная.

Риски для «боя»:
- **Doze / App Standby**: при заблокированном экране и неподвижном телефоне система душит
  `Handler`-таймеры и сетевые вызовы; интервалы «поплывут», уведомление о входе в точку может
  прийти с задержкой. Для FGS-location это смягчено, но не гарантировано на всех прошивках.
- **Убийство процесса** производителем (Xiaomi/Huawei/Samsung агрессивно убивают фоновые
  приложения). После убийства `START_STICKY` перезапустит сервис (см. R5), но `pointsInRange`,
  `lastKnownMessageIds` в памяти обнулятся → возможен повторный показ уведомлений о «новых»
  сообщениях/точках (частично прикрыто кэшем в `SharedPreferences`).
- **Сетевой шторм**: `getPoints()` тянется целиком каждые 30 с без ETag/кэша; на большом числе
  точек это заметный трафик и парсинг на каждом тике.

**Рекомендации (прагматично, без переписывания):** оставить FGS, но
(1) на реальных устройствах проверить поведение при заблокированном экране 30–60 мин;
(2) добавить в онбординг просьбу отключить оптимизацию батареи для приложения
(`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`) — для игрового клиента это оправдано;
(3) не тянуть полный список точек каждые 30 с, если сервер умеет отдавать «изменения».

### R5 (Medium). `START_STICKY` + рестарт с `null` intent

```kotlin
// LocationService.kt:135
return START_STICKY
```

При системном перезапуске `onStartCommand` придёт с `intent == null` → ветка `else` →
`startLocationUpdates()` → `startForeground(...)`. На Android 12+ старт foreground-сервиса из
фона ограничен; для системных рестартов FGS обычно разрешён, но на ряде прошивок/сценариев
(например, если к моменту рестарта отозвано разрешение на локацию) `startForeground` c типом
`location` может кинуть исключение. Часть случаев уже прикрыта: при отсутствии разрешения
сервис делает `stopSelf()` (`:148-152`) — это правильно.

**Починка:** явно обрабатывать `null`-intent как «восстановление», проверять разрешение и
готовность до `startForeground`, и логировать/глушить `ForegroundServiceStartNotAllowedException`
(на API 31+). Рассмотреть `START_REDELIVER_INTENT` или сохранение флага «должен работать» в prefs.

### R6 (Medium). Кулдаун ритуала теряется при повороте/возврате

`performRitual()` блокирует кнопку на 30 минут через поле `isRitualButtonBlocked` и
`binding.btnRitual.postDelayed({...}, 30*60*1000)` (`MainActivity.kt:807`). И поле, и
отложенная задача живут только в текущем экземпляре Activity. При повороте экрана, выходе на
карту и возврате, а тем более при убийстве процесса — блокировка сбрасывается, и «ритуал раз в
30 минут» превращается в «сколько угодно раз». Это не краш, но нарушение игровой механики,
которое участники быстро найдут.

**Починка:** хранить время последнего ритуала в `SharedPreferences`/на сервере и вычислять
доступность по времени, а не по live-таймеру Activity. 30-минутный `postDelayed` на вью — сам
по себе плохая идея (держит колбэк и вью всё это время).

### R7 (Medium). Логирование тел запросов включено всегда

```kotlin
// RetrofitClient.kt:17
.addInterceptor(HttpLoggingInterceptor().apply { level = HttpLoggingInterceptor.Level.BODY })
```

`Level.BODY` логирует полные тела всех запросов/ответов, и это не выключается в release
(тем более что release-сборка сейчас `debuggable true`, см. [06-build-release.md](06-build-release.md)).
Минусы: (1) лишние аллокации/строки на каждом запросе — на слабом телефоне при поллинге это
заметно; (2) в логи попадают id игроков, координаты, содержимое сообщений — см. security.

**Починка:** `Level.BODY` только в debug (`if (BuildConfig.DEBUG) BODY else NONE`).

---

### R8 (Medium). Нет ретраев/бэкоффа и единой обработки ошибок

Каждый вызов сам по себе: `try/catch → лог → вернуть emptyList()/показать Toast`. При
кратковременной потере сети (обычное дело на выезде) экран профиля молча покажет «пустой»
функционал (`checkUserDisciplines` при ошибке скрывает кнопки — `MainActivity.kt:503-538`),
поллинг точек вернёт пустой список и «выведет» игрока из всех зон. Нет ни одной попытки
повторить запрос.

**Починка:** добавить простой ретрай с бэкоффом для ключевых GET (профиль, точки), а на UI —
различать «сеть недоступна» и «сервер ответил пусто», чтобы не прятать кнопки при временном сбое.

### R9 (Low-Med). Возможная утечка `BroadcastReceiver` в апдейтере

`registerReceiver(onComplete, ...)` (`UpdateService.kt:281`) снимается только внутри самого
`onReceive`/таймера при успешной загрузке. Если загрузка зависла или пользователь закрыл экран
до завершения — receiver останется зарегистрированным на переданном `context` (Activity),
удерживая её. Для короткого сценария обновления это некритично, но это утечка.

**Починка:** снимать receiver в `onDestroy`/`finally`; таймер — через `withTimeout`, а не «слепые» 5 с.

---

### R10 (Low-Med). Сеть и диалог обновления в `onStart` при каждом возврате

`onStart()` (`MainActivity.kt:79`) на каждый показ экрана вызывает `checkUserDisciplines()`
(запрос профиля) и `checkForUpdates()` (новый `UpdateService`, запрос JSON). Возврат с карты,
из чата, из профиля — каждый раз пересоздаёт и перезапрашивает. Диалог обновления
(`setCancelable(false)`) может всплыть повторно и перекрыть текущий экран.

**Починка:** проверять обновления один раз за запуск (флаг/дебаунс), а профиль — по разумному TTL.

---

### R11 (Low). Два async-стека и две библиотеки картинок

- **RxJava2 — рудимент**: реально используется только `BehaviorSubject<Location> locationSource`
  (`LocationService.kt:1023`) и подписка в `EkatMaps`. Всё остальное — корутины/Retrofit-callbacks.
  Две парадигмы ради одного моста.
- **Glide и Coil одновременно** и даже в одних файлах (`ImageViewerActivity.kt`,
  `adapters/AttachmentsAdapter.kt`). Обе тянутся в APK. Достаточно одной.

Влияния на стабильность почти нет, но это лишний вес и «когнитивный шум». Дёшево убрать при
случае (заменить `locationSource` на `StateFlow`/callback, оставить одну image-либу).

---

### R12 (Low). Логические мелочи в диффе профиля

`compareProfiles` в блоке «Имя игрока» пишет в `newValue` `characterName` вместо `playerName`
(`LocationService.kt:604`), а следом отдельно сравнивает `characterName`. Пользователь может
получить неверный текст уведомления. Не критично, но это «тихая» ошибка в коде, который шлёт
игроку сообщения.

---

### R13 (Low). Глобальное изменяемое состояние

`ShiftApplication.instance` и `LocationService.instance` — статические ссылки (первая ок для
Application; вторая обнуляется в `onDestroy`). `LocationService.locationSource` — глобальный
`BehaviorSubject`, живёт вечно и хранит последнюю локацию в статике. Для «одноразовой» игры
приемлемо, но это глобальное состояние, которое усложняет рассуждения и может отдавать
устаревшую локацию после рестарта сервиса.

## Что сделано хорошо (не трогать без нужды)

- Везде есть try/catch и деградация вместо краша (пустые списки, показ контента при ошибке).
- Foreground-сервис с типом `location` и уведомлением — правильный выбор под геймплей.
- Проверка runtime-разрешения локации перед `startForeground` и `stopSelf()` при отказе.
- Каналы уведомлений заведены корректно (importance, вибрация), `PendingIntent` с `FLAG_IMMUTABLE`.
- Кэш «уже показанных» сообщений в `SharedPreferences` снижает дубли уведомлений после рестарта.
- Дефолт `isInGame = true` — игрок по умолчанию «в игре», меньше шансов, что забудет включить.

## Приоритет исправлений (для надёжности)

1. **R1** — почини guard `POST_NOTIFICATIONS` (или отвяжи карту от него). Один `if`, но
   спасает всех игроков на Android ≤ 12.
2. **R2** — проверка sha256 перед установкой + один путь завершения загрузки.
3. **R3** — `GlobalScope` → `lifecycleScope` в MainActivity.
4. **R7** — логирование BODY только в debug.
5. **R4/R5** — проверить фон на реальном устройстве с блокировкой экрана; попросить отключить
   оптимизацию батареи.
6. Остальное (R6, R8–R13) — по возможности.
