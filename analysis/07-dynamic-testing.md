# 07. Динамический прогон на эмуляторе

> Устройство: эмулятор `Pixel_6_API_35` (Android 15, API 35), `emulator-5554`.
> Сборка: установленная `versionCode 18 / 2.5` (совпадает с репозиторием).
> Метод: реальные тапы через `adb input`, скриншоты `screencap`, анализ `logcat`.
> Приложение **debuggable** (release), поэтому доступен `run-as` для чтения приватных данных.
>
> Важно: эмулятор — API 35, поэтому баг R1 (`POST_NOTIFICATIONS` на Android ≤ 12) здесь
> не воспроизводится по определению — на этой версии проверка проходит.

«падает при запуске», а характер системных рисков (см. ниже).

## Что подтвердилось вживую (не теория)

### 1. Весь трафик — cleartext HTTP, тела логируются (R7 / S-03 / S-04)
В `logcat` при обычной работе видно:
```
--> GET http://shift96.ru/api_geo/api/v1/points?user_id=MG_Bas
<-- 200 OK http://shift96.ru/messages_api/chats (2092ms)
D/BF/...checkForNewMessagesInChats: Найдено новое сообщение от maksim: запрос инквизиции: ...
D/BF/...checkForNewMessagesInChats: Найдено новое сообщение от pavlik: я же правильно понял...
```
То есть **реальные имена и тексты сообщений игроков пишутся в системный лог** и идут по сети
открытым текстом. Это не гипотеза из кода — это наблюдаемое поведение на живом сервере с
боевыми данными. Плюс `okhttp` логирует полные тела (`<-- END HTTP (37480-byte body)`).

### 2. Поллинг тяжёлый (R4 / R8)
Ответ `points` — **~37 КБ каждые ~30 секунд**, `chats` — ~17 КБ. Список тянется целиком,
без ETag/диффа. За долгую игровую сессию это заметный трафик и постоянный парсинг на телефоне.

### 3. Foreground-сервис стартует корректно
`ActivityManager: Background started FGS: Allowed` — при старте из foreground (переключатель
«В игре») проблем нет. Риск R5 (рестарт с `null`-intent в фоне) на этом сценарии не
воспроизводился — его надо ловить отдельно (убийство процесса + автоперезапуск).

### 4. Клиент рендерит любые строки сервера как есть
В профиле одного игрока одна «дисциплина» пришла битой кракозяброй (`ШЖ╬■┐ ьЮ≈…`) — клиент
показал её без падения, но и без валидации. Для игры не критично, но показывает, что доверие
к данным сервера полное (см. также заметки в security про доверие к серверу).

## Что НЕ удалось проверить в этом прогоне

- **R1 (карта на Android ≤ 12)** — нужен эмулятор/устройство с API ≤ 32. На API 35 не
  воспроизводимо. Логика в коде однозначна (нет guard `SDK_INT >= 33`).
- **Сканеры QR/ауры (камера)** — камера эмулятора ограничена; сканирование артефактов/аур и
  чтение QR отдельно на живой камере не гонялись.
- **Отправка фото в чат** — не тестировалась загрузка крупного вложения (подсистемный отчёт
  указывает на синхронное `readBytes()` на UI-потоке → риск ANR/OOM, [04-subsystems.md](04-subsystems.md)).
- **Поведение в Doze / при заблокированном экране 30–60 мин** — требует долгого прогона на
  реальном устройстве; ключевой тест для «боевой» надёжности фона.
- **Реакция на потерю сети** (самолётный режим во время игры) — стоит прогнать отдельно:
  проверить, что кнопки/зоны не «схлопываются» при временном обрыве (R8).

## Рекомендованные догоняющие проверки перед игрой

1. Прогнать на **реальном Android 11/12** — воспроизвести/закрыть R1 (карта + уведомления).
2. Реальное устройство, **экран заблокирован 30–60 мин** в режиме «В игре»: приходят ли
   уведомления о входе в точку, жив ли сервис, что с батареей.
3. **Самолётный режим** на 1–2 минуты во время сессии: восстанавливается ли всё само.
4. **Отправка тяжёлого фото** в чат МГ (проверить ANR/OOM).
5. Убить приложение из недавних/`Force stop` и проверить автоперезапуск сервиса (R5) и
   отсутствие спама «новых» уведомлений.
